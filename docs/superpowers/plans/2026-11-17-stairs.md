# Stairs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stairs as rectangular bays on a floor that climb to the floor above: automatic step layout (straight, L, U, spiral; landing or winders), slab opening above, warnings, 2D drawing, 3D mass, a drag tool.

**Architecture:** A floor-scoped `stair` entity stores only user parameters. A pure `layoutStair(stair, rise)` derives steps, landings, walking line and opening; validators, 3D and 2D all call it, so steps never go stale. The opening on the floor above is derived from the stairs of the floor below.

**Tech Stack:** TypeScript, vitest (jsdom for plan), three.js, SVG, pnpm.

**Spec:** `docs/superpowers/specs/2026-11-17-stairs-design.md`

## Global Constraints

- XML stays `version="1"`; `<stair>` is optional inside `<floor>`; M1–M5 files load unchanged.
- Step rule: risers `n = ceil(H / 0.18)`, `h = H / n`, tread `b = 0.62 − 2h`, may shrink to `0.60 − 2h` to fit; treads = n − 1 in total; a landing replaces one tread. H = `elevation(above) − elevation(floor)`.
- Local frame: origin at bay centre, +y = climbing direction of the first flight (rotated by `rotation`), first riser on the −y edge; the last riser always lies on a bay edge (slack rules in spec goal 3).
- Winders: 3 per 90°, radiating from the inner corner; walking-line depth (middle of flight) ≥ `0.60 − 2h`.
- Spiral: diameter = min(width, depth), centre column 0.15 m diameter, walking line at 2/3 radius, one full turn must rise ≥ 2.1 m; `left` = counter-clockwise.
- Defaults for `addStair`: `type 'U'`, `turn 'landing'`, `hand 'right'`, `flightWidth 0.9`, `rotation 0`.
- Warnings are non-blocking: `stair-does-not-fit`, `stair-no-floor-above`, `stair-overlaps-wall` (wall outline overlapping the bay interior by > 1 cm² = 1e-4 m²). Blocking: `invalid-stair`.
- Opening on the floor above = the whole bay; applies to its slab and room floors (3D) and is drawn in 2D. Not subtracted from room areas in core.
- 2D labels default `{ up: 'UP', down: 'DN' }` via plan option `stairLabels`; break line at 1.2 m. 3D handrail 0.9 m above nosings; waist ~0.12 m.
- Floor-scoped changes carry `floorId` (M5 model); ids unique per floor. `addFloor` copies stairs with fresh ids.
- Verification: `pnpm test`, `pnpm typecheck`, `pnpm lint`; `npx prettier --check .` stays clean.

## Review Focus

1. A storey height changed after placing a stair: riser count recomputes; a stair that no longer fits gets `stair-does-not-fit` and is drawn as an outline — no throw anywhere (core, 2D, 3D). → Task 4 + Task 5 + Task 6 tests.
2. Rotated bays (90° and 30°): steps, walking line and opening rotate together in layout, 2D and 3D. → Task 2 test (layout), Task 5 test (opening hole position).
3. Undo of `addFloor` / `removeFloor` / `removeStair`: stairs and the opening above come back exactly. → Task 1 + Task 5 tests.
4. A bay on the floor below that crosses a room boundary on the floor above: slab and room-floor geometry still build (no throw, no NaN). → Task 5 test.
5. A stair on a floor whose upper floor is later removed: becomes `stair-no-floor-above`, outline only, and comes back on undo. → Task 4 test.
